# AI XMP Tagger 浏览器本地处理版设计

日期：2026-07-26  
状态：设计完成，等待书面复核  
目标平台：Netlify 静态站点；桌面 Chrome、Edge、Safari 的当前稳定版

## 1. 产品目标

AI XMP Tagger 从“软件下载页”改为可直接使用的网页工具。用户打开网页后选择图片或文件夹，在浏览器本地批量写入或检查 Amazon 所要求的 XMP 关键词：

`contains-synthetic-performer`

成功输出必须在 `XMP dc:subject` 的 `rdf:Bag` 中恰好包含一次该值。图片内容、文件名和处理结果不得上传到 Netlify、GitHub 或其他服务器。

第一版支持：

- JPG / JPEG
- PNG
- 静态或动画 WebP 的原格式标签处理
- BMP 转高清 JPG
- 多文件和文件夹批量处理
- 单文件下载、批量 ZIP、CSV 报告
- 写入后立即重新读取并验证

第一版不支持：

- HEIC / HEIF
- TIFF / TIF
- 视频
- 云端保存、账户、历史记录、团队空间
- 在手机浏览器中承诺大型文件夹处理体验

上述未支持格式继续由桌面版承担，但桌面版下载不再占据网页主流程。

## 2. 方案比较与选择

### 方案 A：纯浏览器本地处理（采用）

Netlify 只提供 HTML、CSS、JavaScript、Web Worker 和自托管 WASM。浏览器通过用户明确选择的 `File` 对象读取图片，在本地生成输出。

优点：

- 图片不离开用户电脑，隐私说明真实、简单。
- 没有图片上传带宽、临时存储和自动删除成本。
- Netlify 静态部署足够，维护面较小。
- Mac 和 Windows 使用相同网页。

代价：

- 浏览器不能复用桌面版的原生 ExifTool 和 Sharp。
- 需要实现并严格测试 JPEG、PNG、WebP 的 XMP 容器写入。
- HEIC、TIFF 和极大批次延后。

### 方案 B：服务器处理（不采用）

图片上传到服务器，由 ExifTool 和 Sharp 处理。格式兼容性最好，但带来隐私、存储清理、带宽、超时、费用和合规问题。

### 方案 C：混合处理（不采用）

普通格式本地处理，失败格式上传服务器。功能最多，但隐私规则不易解释，测试矩阵和维护成本最高，不适合作为第一版。

## 3. 用户界面

网站使用单页工作台，而不是营销页或软件下载页。

从上到下依次为：

1. 标题和一句用途说明。
2. 始终可见的“浏览器本地处理，不上传图片”状态标识。
3. 三张处理模式卡片。
4. 拖放区、“选择图片”和“选择文件夹”按钮。
5. 待处理清单、格式统计、总大小和批次风险提示。
6. “开始处理”按钮。
7. 进度、取消按钮和逐文件结果表。
8. 单文件下载或批量 ZIP、CSV 报告按钮。
9. macOS / Windows 独立验证说明、格式矩阵、批量限制、隐私说明和 FAQ。

默认选中“高清 JPG＋写入 XMP”。页面在处理开始前不请求文件系统写权限；所有文件都必须由用户主动选择或拖入。

桌面端是主要使用场景。页面保持响应式，手机可以处理少量文件，但在手机上不显示“选择文件夹”为主操作，也不承诺大型批次。

## 4. 三种模式

### 4.1 高清 JPG＋写入 XMP（默认）

| 输入 | 行为 | 输出 |
|---|---|---|
| JPG / JPEG | 不解码、不重新压缩；仅更新标准 XMP APP1 段 | JPG |
| PNG | 解码、透明区域铺白、转 sRGB、编码高质量 JPG，再写 XMP | JPG |
| WebP | 静态 WebP 解码并转高质量 JPG；动画 WebP拒绝转换并建议“保持原格式” | JPG |
| BMP | 使用受限的纯 JavaScript BMP 解码器，转高质量 JPG，再写 XMP | JPG |

JPG 输入的压缩扫描数据必须逐字节保持不变；“画质不变”只用于这一分支。PNG、WebP、BMP 转 JPG 属于有损重新编码，界面必须写“高清”，不得写“无损”。

转换设置：

- JPEG 质量：100
- 色度采样：4:4:4
- 渐进式：关闭
- 透明背景：白色
- 输出方向：物理像素已转正
- 输出颜色空间：sRGB
- 嵌入标准 sRGB ICC 配置文件

转换输出不复制 GPS、相机型号等 EXIF 数据。若输入存在有效 `dc:subject`，只保留其中的关键词并加入目标关键词；其他描述性元数据第一版不复制，以减少隐私泄露和容器兼容风险。

### 4.2 保持原格式＋写入 XMP

| 输入 | 行为 |
|---|---|
| JPG / JPEG | 更新标准 XMP APP1，其他段和图像数据不变 |
| PNG | 更新或加入 XMP `iTXt` 数据块，其他数据块不变 |
| WebP | 更新或加入 `XMP ` RIFF 数据块，修正 RIFF 长度和 VP8X XMP 标志，其他数据块和帧不变 |
| BMP | 不处理；解释 BMP 无法可靠嵌入标准 XMP，并建议默认模式 |

动画 WebP 可以在本模式中写标签，因为图像帧不解码、不改变。

### 4.3 只检查 XMP

支持读取 JPG、PNG 和 WebP。检查结果分为：

- 正确：字段存在，目标关键词恰好一次。
- 缺少字段：没有显式 `XMP dc:subject`。
- 缺少关键词：字段存在，但没有目标关键词。
- 重复：目标关键词多于一次。
- 无法检查：格式不支持、容器损坏、XMP XML 无效或超出安全限制。

只检查模式不得生成修改后的图片。BMP 返回“该格式没有可靠的嵌入式 XMP 检查路径”。

## 5. XMP 数据模型和容器写入

### 5.1 共同规则

- 使用 UTF-8 XMP Packet。
- `dc:subject` 必须表示为 `rdf:Bag`。
- 保留现有非目标关键词的顺序。
- 将多个目标关键词归一化为一个。
- 不允许 `DOCTYPE`、外部实体或超出限制的 XML。
- 写入后重新从输出二进制中解析，只有字段存在且目标值恰好一次才标记成功。
- 标准 XMP Packet 上限为 60 KiB；超过 JPEG APP1 安全容量或出现 Extended XMP 时，原格式写入失败并给出明确建议，不静默丢弃元数据。

### 5.2 JPEG

- 验证 SOI、段长度、SOS 和 EOI 结构。
- 识别 `http://ns.adobe.com/xap/1.0/\0` 标准 XMP APP1。
- 有一个有效标准 Packet 时原位替换该段。
- 没有 Packet 时在现有 JFIF / EXIF / ICC 元数据区之后、图像扫描数据之前插入 APP1。
- 多个标准 Packet、损坏段或 Extended XMP 返回可解释错误。
- 通过 Blob 分片拼装输出，避免对图像像素解码。

### 5.3 PNG

- 验证 PNG 签名、数据块边界和 CRC。
- XMP 使用关键字为 `XML:com.adobe.xmp` 的未压缩 `iTXt` 数据块。
- 替换唯一有效 XMP 块，或在 `IEND` 前插入。
- 多个 XMP 块不自动合并，返回冲突错误。
- 重写的数据块必须重新计算 CRC；其他数据块字节不变。

### 5.4 WebP

- 验证 RIFF / WEBP 头、偶数字节填充和数据块边界。
- XMP 使用 FourCC `XMP `，第四个字符为空格。
- 最多保留一个 XMP 块。
- 更新 RIFF 总长度。
- 存在 VP8X 时设置 XMP metadata feature bit。
- 简单 VP8 / VP8L 文件需要加入合规 VP8X 块，宽高从受验证的位流头读取；原图像数据块保持不变。
- 动画、ICC、EXIF 和未知 RIFF 块保持顺序和原始字节。

## 6. 浏览器处理架构

代码分为清晰模块：

- `file-intake`：文件/文件夹选择、拖放、MIME 魔数识别、去重和相对路径清理。
- `batch-policy`：数量、大小、像素和设备风险检查。
- `format-inspection`：识别 JPEG、PNG、WebP、BMP 及动画状态。
- `xmp-model`：安全解析、关键词归一化、RDF 序列化。
- `jpeg-xmp`、`png-xmp`、`webp-xmp`：各容器的读取、写入和验证。
- `image-conversion`：PNG / WebP / BMP 解码、方向和颜色处理、WASM JPEG 编码。
- `worker-protocol`：主线程和 Web Worker 的可取消消息协议。
- `batch-runner`：调度、逐文件隔离、进度和取消。
- `output-package`：安全文件名、相对目录、ZIP 和 CSV。
- `ui`：工作台状态和无障碍交互，不直接解析二进制。

元数据写入和图片转换在 Web Worker 中运行。转换任务同一时间最多一个；只修改元数据的任务最多并行两个。调度器根据任务类型分流，避免多张大图同时解码。

所有 WASM、字体、图标和脚本都随站点同源提供。运行时不从 CDN 加载处理代码。

## 7. 批量边界

第一版使用可解释的固定上限：

- 每批最多 300 个文件。
- 单文件最多 50 MB。
- 每批输入总大小最多 500 MB。
- 需要解码的图片最多 40,000,000 像素。
- 超过 100 个文件或 250 MB 时先显示黄色提示，仍可继续。
- 超过硬上限时不开始处理，建议拆分批次或使用桌面版。

这些是浏览器稳定性上限，不是 Netlify 上传限制，因为图片不会上传。

用户可以取消尚未开始的任务。当前正在编码的单个任务完成或安全中止后停止。取消不会删除已经生成且仍保存在内存中的成功结果。

## 8. 输出和命名

- 一个成功输出：直接下载图片，并单独提供 CSV。
- 多个成功输出：生成 `AI_XMP_Output_YYYYMMDD-HHmm.zip`。
- ZIP 内保留经过清理的输入相对目录。
- 输出文件名默认添加 `_xmp`，不伪装覆盖原文件。
- 同名冲突使用 `_xmp-2`、`_xmp-3`。
- 清理绝对路径、盘符、`..`、控制字符、Windows 保留名和前导分隔符，防止 Zip Slip。
- ZIP 根目录包含 UTF-8 BOM CSV 报告。
- 报告只保存文件名和相对路径，不包含本机绝对路径。

成功结果只存在于当前页面内存中。刷新、关闭页面或标签页崩溃后不可恢复，界面必须在用户离开前提示先下载。

## 9. 错误处理

每个文件独立返回结果，单个失败不终止整批。错误分类包括：

- 格式不支持
- 文件魔数与扩展名不一致
- 文件或像素超过限制
- 容器损坏
- XMP XML 无效
- 多个 XMP Packet 冲突
- Extended XMP 暂不支持
- 图片解码失败
- JPEG 编码失败
- XMP 写入后验证失败
- ZIP 生成失败
- 用户取消

错误文字必须包含下一步建议，例如切换默认模式、拆小批次或使用桌面版；不得只显示技术堆栈。

## 10. 隐私和安全

- 站点不提供上传端点。
- 不集成分析、广告、错误上报、聊天组件或第三方字体。
- 文件只来自用户明确选择或拖入的 `File` 对象。
- 不读取浏览历史、剪贴板或任意本机路径。
- 处理日志仅在页面内存中。
- 转换模式默认移除 EXIF / GPS。
- HTML 中明确说明：Netlify 会像普通网站一样收到页面和静态资源请求，但不会收到用户选择的图片、文件名或处理结果。
- 内容安全策略默认 `default-src 'self'`，允许同源脚本、同源 WASM、Blob Worker 和 Blob 下载；禁止对象、框架、表单提交和外部连接。
- **2026-07-26 CSP 勘误：** `connect-src` 必须设为 `'self'`，因为生产 Worker 会通过同源请求读取带哈希的自托管 MozJPEG WASM。该设置不允许第三方来源，也不改变“图片、文件名和处理结果不上传”的隐私边界。
- 依赖锁定精确版本，公开软件物料清单和许可证清单。

## 11. 测试与验收

### 11.1 单元和属性测试

- XMP 关键词保留、追加、去重和 XML 安全限制。
- JPEG 段、PNG 数据块、WebP RIFF 数据块的正常、截断、溢出和随机损坏输入。
- PNG CRC、WebP RIFF 长度和 VP8X 标志。
- 文件名和相对路径清理。
- 批量上限、取消和错误隔离。

### 11.2 互操作测试

对每种支持容器保留真实小型 fixture：

- 无 XMP
- 已有其他关键词
- 已有目标关键词
- 重复目标关键词
- EXIF / ICC / IPTC 和未知块
- 动画 WebP
- 带方向信息的转换输入
- 有透明通道的 PNG / WebP

浏览器生成输出后，使用独立 ExifTool 读取 `XMP-dc:Subject`，必须恰好出现一次目标关键词。JPEG 默认模式还要比较写入前后的压缩扫描数据 SHA-256，证明没有重新编码。PNG / WebP 原格式模式比较除目标 XMP 和必要容器头之外的数据块。

### 11.3 图片质量测试

- 转换后宽高与物理方向正确。
- 透明区域为白色。
- 输出为 sRGB 并包含 ICC。
- JPEG 使用质量 100、4:4:4、非渐进式。
- 不使用“无损转换”描述非 JPG 输入。

### 11.4 浏览器端到端测试

Playwright 覆盖：

- 拖入和选择文件。
- 三种模式和格式限制。
- 批量进度、取消、部分失败。
- 单文件下载、ZIP 内容和 CSV。
- 键盘操作、焦点、读屏标签和窄屏布局。
- 断网后已加载页面仍能完成当前批次。
- 网络监听断言处理期间没有图片上传请求。

## 12. Netlify 部署

- Vite 构建输出为 `dist`。
- Netlify 构建命令为 `npm run build`，发布目录为 `dist`。
- Node 版本固定为 24。
- 使用 Netlify 默认 HTTPS 子域名作为第一版正式地址。
- 配置严格安全响应头和长期缓存的哈希静态资产。
- HTML 使用短缓存，避免旧版本长期滞留。
- 发布前在真实 Mac Chrome / Safari 和真实 Windows Edge / Chrome 各完成一次端到端处理，并用独立 ExifTool 验证输出。

GitHub 公共仓库继续保存网页源码和测试。GitHub Release 中的桌面安装包作为 HEIC、TIFF、超大批次和离线长期使用的备用方案，不作为首页主按钮。

## 13. 上线验收标准

满足以下条件才可公开：

1. JPG 默认模式在 100 个以上不同 fixture 上证明图像扫描数据未改变。
2. JPG、PNG、WebP 的输出均通过独立 ExifTool 验证。
3. PNG、WebP、BMP 转 JPG 的尺寸、方向、透明背景和颜色测试通过。
4. 三种模式的支持矩阵与界面完全一致。
5. 一张失败不会中断其他文件。
6. 批量 ZIP 无绝对路径、无 Zip Slip、CSV 无本机路径。
7. 浏览器网络审计证明处理期间没有图片上传。
8. Netlify 线上 CSP、缓存和 MIME 类型正确。
9. Mac 与 Windows 的真实浏览器冒烟通过。
10. 页面明确说明这是独立工具，不是 Amazon 官方产品。

## 14. 依据

- Adobe XMP Specification Part 3 定义 XMP Packet 在文件容器中的存储方式。
- Google WebP RIFF Container Specification 定义 `XMP ` 数据块、VP8X 特性位和 RIFF 结构。
- 浏览器 File / Blob API 只允许网页访问用户明确选择的文件，并可在 Web Worker 中处理。
- Netlify 静态生产部署足以承载不含上传端点的 Vite 应用。
